# Практика 4 Миграция Mattermost

Ветка `migration` содержит перенос Mattermost 9.5.0 с MySQL 8.0 на Mattermost 12.0.1 с PostgreSQL 15. Предыдущая практика на порту 8080 сохраняется. Mattermost доступен по адресу http://localhost:8065.

## Структура

- `legacy/docker-compose.yml` — исходное приложение и MySQL.
- `docker-compose.prod.yml` — Mattermost 12.0.1 и PostgreSQL 15.
- `.github/workflows/migration.yml` — автоматизация на self-hosted runner MacBook-Pro-Egor-practice.
- `scripts/migration/` — бэкап, перенос, проверка и сбор результатов.
- `tests/mattermost.spec.cjs` — проверка исходных сообщений в браузере после переноса.

## Подготовка исходных данных

Локальный `.env.migration` создан отдельно от настроек предыдущей практики. Пароли также добавлены в GitHub Secrets: DB_MYSQL_ROOT_PASSWORD, DB_MYSQL_PASSWORD, DB_POSTGRES_PASSWORD и MM_ADMIN_PASSWORD.

```sh
docker compose --env-file .env.migration -f legacy/docker-compose.yml up -d --wait
python3 scripts/migration/seed_legacy.py
```

Скрипт создаёт учебного администратора `practiceadmin`, команду «Практика DevOps», приватный канал «Проверка миграции», пять тестовых сообщений, контрольное вложение и аватар. Их исходные ID и контрольные суммы сохраняются вне Git.

После успешного переноса не запускайте старое приложение поверх тех же пользовательских файлов. Оно оставлено в конфигурации как исходный стенд и образец настройки.

## Работа workflow

1. Создать рабочий файл окружения из GitHub Secrets.
2. Проверить постоянный флаг завершения миграции.
3. Если флага нет: остановить запись приложения, сохранить согласованный SQL dump и архив пользовательских файлов.
4. Создать PostgreSQL и подготовить его схему с помощью официального migration-assist v0.8 для исходной версии Mattermost.
5. Перенести записи официальным образом Mattermost pgloader. Используется флаг `include drop`; дополнительный сброс незавершённой целевой схемы позволяет повторить попытку после ошибки.
6. Восстановить индексы, запустить Mattermost 12.0.1 и удалить контейнер MySQL командой Compose с `--remove-orphans`.
7. Проверить пользователя, приватный канал, исходные ID и тексты сообщений, SHA256 вложения и аватара, состояние контейнеров и отображение сообщений в браузере.
8. Только после успешных проверок записать флаг завершения.
9. Сохранить отчёт, скриншот и логи с замаскированными паролями.

## Идемпотентность и данные

Постоянное состояние находится в `~/Library/Codex/mattermost-practice/state/`, вне checkout runner. Поэтому очистка репозитория при следующем запуске не удаляет маркер или резервные копии.

Флаг `.migration_completed` связан с system_identifier конкретной PostgreSQL. Повторный успешный запуск пропускает бэкап и перенос, но снова разворачивает приложение и проверяет данные. Если флаг есть, а нужная база потеряна, workflow останавливается с ошибкой вместо ложного пропуска миграции.

При неудачной первичной миграции MySQL volume сохраняется. Повторная попытка поднимает исходную базу и заново создаёт только незавершённую целевую схему. После завершённой миграции сброс целевой схемы запрещён скриптом.

Том `mattermost_practice_data` используется обеими версиями приложения. В нём хранятся вложения и аватары. SQL dump и архив файлов остаются в приватном каталоге резервных копий и не загружаются в публичные артефакты.

## Демонстрация

GitHub → Actions → Idempotent Mattermost migration and upgrade → Run workflow → ветка migration. Два запуска подряд должны быть успешными. Во втором шаги бэкапа и переноса будут Skipped.

```sh
docker ps
curl -f http://localhost:8065/api/v4/system/ping
docker compose --env-file .env.migration -f docker-compose.prod.yml logs --tail=20
```

В веб-интерфейсе откройте команду «Практика DevOps» и приватный канал «Проверка миграции». Проверьте исходные сообщения, вложение и аватар.

## Отличия от примера задания

Исправлены имя Docker-образа, mysql-драйвер, пути macOS и имя сети. Оба Compose-файла используют один project name, чтобы `--remove-orphans` удалял старый сервис. Официальная подготовка схемы PostgreSQL сохраняет типы и индексы Mattermost; версия приложения обновляется после переноса данных. Маркер записывается после проверки результата. Ожидание готовности заменяет фиксированную паузу.
